# infra

Deux choses vivent ici : la description Terraform de l'infrastructure, construite lot par lot (chantier Terraform de [`../docs/roadmap.md`](../docs/roadmap.md)), et la configuration de service du site Firebase Hosting, que le pipeline envoie avec chaque version.

| Fichier | Ce qu'il décrit | Comment il s'applique |
|---|---|---|
| `firebase-hosting.json` | configuration de service du site Firebase Hosting (repli SPA, en-têtes de sécurité, paliers de cache) | envoyée avec chaque version par [`../scripts/publish-front-firebase.mjs`](../scripts/publish-front-firebase.mjs), section Hosting ci-dessous |

## Les identifiants sont des espaces réservés

Le dépôt est public : aucun identifiant de projet ni de bucket n'y est écrit. Les fichiers portent des gabarits `<COMME_CECI>`, **à substituer avant d'appliquer**, jamais à committer remplis.

| Gabarit | Où se relève la valeur |
|---|---|
| `<PROJET_GCP>` | `gcloud config get-value project` |
| `<BUCKET_TFSTATE>` | `TF_STATE_BUCKET` du `.env` local, ou `gcloud storage buckets list` |

Les secrets de déploiement (`GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT`, `GCP_PROJECT_ID`, `VITE_*`) vivent dans les environnements GitHub (`Settings / Environments`), un par identité GCP, section Identités : **production** et **staging** pour les deux étapes du déploiement, **backup** pour la sauvegarde, **infra-apply** pour l'`apply` Terraform, **infra-plan** pour le `plan` d'une pull request. Tous sont réservés à la branche `master`, sauf `infra-plan`, qu'une pull request doit pouvoir utiliser. Seuls `SONAR_TOKEN` et `SENTRY_AUTH_TOKEN` (DEBT-027) sont encore des secrets de dépôt (`Settings / Secrets and variables / Actions`), où vivent aussi les variables. Un secret ne se relit pas après sa création, seulement se remplacer : `gh secret set <NOM> --env production`.

## Terraform

```
infra/terraform/
├─ modules/
│  ├─ artifact-registry/   dépôt Docker des images de l'API et sa rétention (10 versions gardées, purge à 30 jours)
│  ├─ secrets/             les secrets de l'API dans Secret Manager, conteneurs seuls, et le droit de lecture de l'identité d'exécution
│  ├─ cloud-run-api/       le service Cloud Run de l'API, son invocation publique et son domaine
│  ├─ web-hosting/         le site Firebase Hosting du front (provider google-beta)
│  ├─ github-federation/   le pool et le provider OIDC qui font confiance aux workflows du dépôt, environnement par environnement
│  ├─ workload-identity/   un compte sans clé que GitHub assume depuis un seul environnement, et chaque droit du compte, lié à sa ressource
│  └─ monitoring/          les trois sondes, les six politiques d'alerte, le canal e-mail et le tableau de bord
└─ environments/
   ├─ production/          module racine : main.tf (les API du projet, l'identité d'exécution, celle du planificateur, le bucket de sauvegarde, le lien contre la suppression du projet, les journaux d'audit de Secret Manager, les modules, l'activation de Firebase), versions.tf, backend.tf, providers.tf, variables.tf, outputs.tf, .terraform.lock.hcl
   └─ staging/             module racine de la recette : les mêmes modules, suffixés -staging, liés à la fédération et au dépôt d'images de la production par son état distant
```

Les providers portent `user_project_override` et `billing_project` : les API Firebase refusent un jeton utilisateur sans projet de quota, et c'est un jeton utilisateur (`gcloud auth print-access-token`) que l'enveloppe fournit. Activer Firebase sur le projet (`google_firebase_project`) a demandé une fois d'accepter les conditions Firebase dans la console avec le compte propriétaire, l'API répond 403 avant : la ressource a été importée, pas créée.

Un module racine par environnement, un état distant par module racine (préfixe `environments/<nom>` dans le bucket d'état) : la production, et depuis le lot 8 la recette, qui instancie les mêmes modules (section Recette). Rien n'est écrit dans les fichiers `.tf` qui identifie le projet : l'identifiant du projet est une variable, le nom du bucket d'état est fourni à `init`.

### Ce que Terraform décrit, ce que le pipeline garde

La production a été **importée** le 2026-09-18 (lot 2 : 32 ressources, `plan` vide depuis), jamais recréée. Le partage avec `deploy.yml`, qui continue de déployer :

- **Terraform décrit la forme** : dépôt d'images et sa rétention, les quatorze secrets et le droit `secretAccessor` de l'identité d'exécution sur chacun, le service Cloud Run (identité, ingress, plafond d'instances, CPU et mémoire, concurrence, délai, port), son invocation par `allUsers` et son domaine `api.movie-picker.fr`.
- **Le pipeline garde le conteneur** : l'image, les variables d'environnement et les secrets montés (`--set-secrets`, `--set-env-vars`, dont `ALLOWED_ORIGINS`, variable GitHub, `SENTRY_RELEASE`, qui change à chaque déploiement, et `SCHEDULER_OIDC_*`, l'audience et l'identité que les routes `/scheduler/*` exigent), le trafic (`--no-traffic` puis promotion, épinglage par `rollback.yml`) et les marqueurs `client` / `client_version` posés par gcloud. Le module `cloud-run-api` les écrit à la création d'un service (recette) puis les ignore (`lifecycle.ignore_changes`) : un `plan` reste vide après un déploiement ou un retour arrière. Les faire passer sous Terraform demanderait d'abord que la version voyage dans l'image plutôt qu'en variable ; ce n'est pas dans le chantier, DEBT-044 en garde la trace.
- **Le pipeline garde aussi les trois jobs Cloud Scheduler** de la production, qu'il crée ou met à jour après chaque promotion de l'API : ils signent un jeton OIDC avec `movie-picker-scheduler@` (décrit ici, sans aucun rôle) pour l'audience de l'API publique, et l'API vérifie l'émetteur Google, l'audience et cette adresse. Plus aucun secret partagé ne voyage ; les décrire ici demande d'abord que la révision de production accepte ce jeton, DEBT-037 dit dans quel ordre.
- **Les versions des secrets ne passent jamais par Terraform** (`gcloud secrets versions add`), sinon leur valeur finirait dans l'état. Les secrets et le service portent `deletion_protection` : retirer un secret de la liste ou détruire le service demande d'abord de lever ce verrou dans le code.
- Le montage d'un secret dans le service reste décrit à deux endroits, la liste `SECRETS` de `deploy.yml` et `api_secret_names` dans `main.tf`, le premier faisant foi (DEBT-044) : ajouter un secret, c'est le créer ici (`apply`), lui ajouter une version à la main, puis l'ajouter à `deploy.yml`.

### Lancer Terraform

Terraform n'est pas installé sur le poste : il tourne depuis son image Docker épinglée par digest dans [`../scripts/terraform.mjs`](../scripts/terraform.mjs), et c'est cette image que tout le monde utilise, la porte locale comprise. Docker Desktop lancé et `gcloud auth login` fait, puis :

```bash
pnpm run terraform -- init
pnpm run terraform -- plan
pnpm run terraform -- --root production plan   # même chose, la racine par défaut est production
pnpm run terraform -- --root staging plan      # la recette, après un init avec --root staging
pnpm run terraform -- fmt -recursive           # fmt s'applique à tout infra/terraform/
pnpm run terraform -- providers lock           # après un changement de version de provider
```

Ce que l'enveloppe ajoute d'elle-même :

- à `init`, le bucket d'état (`-backend-config=bucket=…`), lu dans `TF_STATE_BUCKET` (variable d'environnement, sinon `.env` à la racine du dépôt) ; `-backend=false` s'en passe, c'est ce que font la porte locale et la CI ;
- `TF_VAR_project_id`, lu dans `GCP_PROJECT_ID` (variable d'environnement, sinon `.env`), sinon le projet actif de gcloud ; `TF_VAR_state_bucket` depuis `TF_STATE_BUCKET` et `TF_VAR_alert_email` depuis `ALERT_EMAIL`, deux valeurs que les modules racines attendent et que le dépôt ne porte pas (la recette ignore la seconde, elle ne déclare pas la variable) ;
- `GOOGLE_OAUTH_ACCESS_TOKEN`, obtenu par `gcloud auth print-access-token` pour toute commande qui parle à GCP : aucun fichier de clé sur le poste, le jeton dure une heure et passe à Docker par son nom, jamais sur sa ligne de commande ;
- à `providers lock` sans `-platform`, les cinq plateformes (linux et darwin en amd64 et arm64, windows amd64) : sans elles le fichier de verrouillage ne porterait que l'empreinte `h1:` de linux_amd64 et `init -lockfile=readonly` refuserait le cache des providers partout ailleurs.

Les providers sont mis en cache dans le volume Docker `movie-picker-terraform-plugins`, et le dossier de travail `.terraform/` de chaque racine vit dans `movie-picker-terraform-data` (la porte y a le sien, à part, pour que le backend configuré par `init` ne lui soit jamais demandé) : un montage Windows ne porte pas les liens symboliques que Terraform crée vers son cache, et rien de tout cela n'a sa place dans l'arbre de travail. Seul `.terraform.lock.hcl` s'écrit à côté de la configuration, et il est versionné. Effacer ces deux volumes ne perd rien : `init` les remplit à nouveau.

### État distant

L'état est dans un bucket Cloud Storage versionné (chaque `apply` en garde l'ancienne version) et verrouillé (le backend `gcs` pose un verrou le temps d'une écriture, deux `apply` concurrents ne peuvent pas se croiser). Le bucket lui-même n'est pas décrit en Terraform, on ne peut pas décrire l'endroit où l'on range la description : il se crée une fois, à la main.

```bash
gcloud storage buckets create gs://<BUCKET_TFSTATE> --location=europe-west1   --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets update gs://<BUCKET_TFSTATE> --versioning
printf '{"rule":[{"action":{"type":"Delete"},"condition":{"isLive":false,"daysSinceNoncurrentTime":90}}]}' > /tmp/lifecycle.json
gcloud storage buckets update gs://<BUCKET_TFSTATE> --lifecycle-file=/tmp/lifecycle.json
```

puis, dans le `.env` local (ignoré par git, en liste blanche de gitleaks) :

```
TF_STATE_BUCKET=<BUCKET_TFSTATE>
GCP_PROJECT_ID=<PROJET_GCP>
ALERT_EMAIL=<ADRESSE_DES_ALERTES>
ALERT_SMS_NUMBER=<NUMERO_E164_OU_VIDE>
```

La règle de cycle de vie ne supprime que les versions non courantes de plus de 90 jours ; la version courante de l'état ne s'efface jamais d'elle-même. L'état porte tout ce que les ressources exposent, valeurs de secrets comprises quand Terraform les lit : accès public interdit, accès uniforme au niveau du bucket, et seuls le compte propriétaire du projet, `movie-picker-terraform@` (lecture et écriture, depuis master) et `movie-picker-terraform-plan@` (lecture seule, depuis une PR) y accèdent, les deux derniers par des liaisons décrites dans le module racine (`state_bucket`). Les liaisons de convenance que Cloud Storage pose à la création d'un bucket (`projectViewer`, `projectEditor` en `legacyObjectReader` et consorts) ont été retirées des deux buckets le 2026-09-20 : elles donnaient la lecture des objets à toute identité porteuse d'un rôle de base sur le projet, et rien dans Terraform ne les montrait. `pnpm run check:iam` (section Portes) les signalerait si elles revenaient.

### Front sur Firebase Hosting (lot 3)

Le site `movie-picker-web` (module `web-hosting`) est la cible de `deploy-front` dans `deploy.yml` : une version publiée, puis vérifiée sur `https://movie-picker-web.web.app` et sur le domaine public (`verify-front`, première origine d'`ALLOWED_ORIGINS`, point d'entrée du build comparé à celui servi).

- **Publication** : [`../scripts/publish-front-firebase.mjs`](../scripts/publish-front-firebase.mjs) parle à l'API REST Hosting (version créée avec la configuration, fichiers gzippés et hachés, envoi des seuls inconnus, finalisation, release), sans `firebase-tools`, avec le même jeton que le reste du pipeline ; dans `deploy-front` la version est étiquetée `commit` et `run_id`. En local : `GCP_PROJECT_ID=<PROJET_GCP> node scripts/publish-front-firebase.mjs --site movie-picker-web` après `pnpm --filter web build` (`--dry-run` liste les fichiers sans rien envoyer). Chaque version est immuable et les releases restent listées : `rollback-front.yml` ([`../scripts/rollback-front-firebase.mjs`](../scripts/rollback-front-firebase.mjs)) remet en service la version précédente, ou celle d'un commit, en une release, sans archive ni republication ; seules les versions étiquetées par le pipeline sont éligibles.
- **Parité avec l'ancien CloudFront**, vérifiée le 2026-09-19 en-tête par en-tête sur `/`, une route prérendue, un chemin inconnu, un actif haché, `sw.js`, le manifeste, `sitemap.xml`, `robots.txt` et une icône : mêmes six en-têtes de sécurité, mêmes trois paliers à l'origine (`immutable` un an sur `assets/`, `icons/`, `avatars/`, les images et `robots.txt` ; une heure sur `sitemap.xml` ; `no-cache, must-revalidate` partout ailleurs, `no-store` en plus sur `sw.js`) ; depuis le 2026-09-21 les fichiers à chemin fixe que `index.html` et le manifeste citent sans empreinte (`favicon.svg`, `logo.svg`, `og-image.png`) sont à un jour et `robots.txt` à une heure comme le sitemap, parce qu'un `immutable` d'un an sur un chemin qui ne change pas de nom cachait toute retouche aux navigateurs pendant un an, même repli SPA en 200. Deux écarts, dans le bon sens : `/decouvrir/` répond `301` vers `/decouvrir` au lieu de servir la coquille (DEBT-043) ; les scripts partent en `text/javascript` et le sitemap en `application/xml` sans charset, deux libellés équivalents. Le `Strict-Transport-Security` est celui de la configuration : Hosting n'impose le sien (`max-age=31556926; includeSubDomains; preload`) que sur l'adresse `web.app`, vérifié le 2026-09-20 sur les quatre domaines personnalisés, qui servaient jusque-là un `max-age` nu ; la configuration porte donc `includeSubDomains; preload` elle-même. La politique de sécurité du contenu, elle, voyage dans le document (balise `meta` posée au build par `apps/web/vite.config.ts`) : ses scripts en ligne sont autorisés par empreinte SHA-256 calculée sur le document final, jamais par `'unsafe-inline'`.
- **Ce que la configuration encode** (`firebase-hosting.json`) : les routes prérendues sont publiées comme `<route>/index.html`, que Hosting sert à l'adresse de la route (`trailingSlashBehavior: REMOVE`), là où S3 demandait une clé sans extension ; `cleanUrls` reste faux ; le repli `**` vers `/index.html` ne joue que pour les chemins sans fichier. Pour les en-têtes, quand plusieurs règles s'appliquent à un chemin, **la dernière règle du fichier l'emporte** sur une clé dupliquée, vérifié : la règle `**` pose la base et les règles suivantes la précisent, garder cet ordre.
- **Identité du pipeline** : `roles/firebasehosting.admin` fait partie des droits du compte CI (module `workload-identity`, instance `ci`, section Identités). Les appels envoient `x-goog-user-project`, exigé avec un jeton utilisateur et sans effet avec celui du compte de service.

### Domaines (lot 4, bascule du 2026-09-20)

Le module `web-hosting` décrit trois domaines : `www.movie-picker.fr`, canonique et servi, et `web.movie-picker.fr` plus l'apex, qui répondent `301` vers `www` en gardant le chemin (`redirect_target`) : les liens `/e/<slug>` et les courriels envoyés du temps de `web` continuent d'arriver. Le DNS est chez OVH, sans CLI : chaque enregistrement se pose dans le manager, et `pnpm run terraform -- output web_dns` dit pour chaque domaine son état (`host_state`, `ownership_state`, `cert_state`) et les enregistrements que Hosting attend encore. Un sous-domaine se prouve et se sert par un seul CNAME vers `<site>.web.app` ; l'apex demande un A `199.36.158.100` et un TXT `hosting-site=<site>`, qui couvre aussi les sous-domaines.

Ce qui a permis la bascule sans coupure, à rejouer pour un domaine déjà servi ailleurs : Hosting expose dans `cert.verification` de l'API un défi ACME par TXT (`_acme-challenge.<hôte>`) ou par HTTP (chemin `/.well-known/acme-challenge/<jeton>` sur le site en service). Le défi HTTP servi depuis l'ancien hébergement fait passer le certificat `CERT_ACTIVE` avant que le DNS ne bouge ; le certificat `TEMPORARY` affiché avant cela ne couvre pas le domaine. Un `hostState` à `HOST_MISMATCH` avec un certificat `CERT_VALIDATING` est l'état normal d'un domaine décrit dont le DNS n'a pas encore bougé.

AWS est vide depuis le 2026-09-20 : distribution (désactivée, puis supprimée une fois déployée), bucket, certificat wildcard (il ne servait que cette distribution, vérifié par `aws acm describe-certificate`), politique d'en-têtes, WAF, contrôle d'accès à l'origine, rôle et fournisseur OIDC supprimés ; les secrets et variables `AWS_*` retirés de GitHub et `ALLOWED_ORIGINS` réduit aux deux domaines servis. Ne reste que l'utilisateur IAM `movie-picker-ops` de la CLI locale, qui ne sert plus qu'à fermer le compte. La sonde de disponibilité du front (Cloud Monitoring) vise `www` : un `monitoredResource` ne se modifie pas, la sonde a été recréée et la politique « Front indisponible » repointée sur son `check_id`.

### Identités (lots 5 et 6, posés le 2026-09-20, frontières resserrées le même jour)

Huit comptes de service décrits, aucune clé : `gcloud iam service-accounts keys list --managed-by=user` ne rend rien sur aucun compte du projet, et rien ne doit en créer. Un environnement GitHub par identité assumée, et une identité par environnement : le provider n'accepte que les sujets `repo:<dépôt>:environment:<nom>` de la table, chacun lié à un seul compte par sa liaison `workloadIdentityUser`, et, pour tous sauf `infra-plan`, seulement depuis `refs/heads/master` (`assertion.ref`), doublure de la politique de branche des environnements. Un job d'un autre environnement, même accepté par le provider, ne peut pas assumer un compte qui n'est pas le sien : un job de déploiement compromis ne peut ni administrer l'IAM du projet, ni lire la base, ni planifier autre chose que ce qu'il déploie.

| Environnement GitHub | Compte assumé | Workflow |
|---|---|---|
| `production` | `movie-picker-ci@` | `deploy.yml` (étape `production`), `rollback.yml`, `rollback-front.yml`, `cloud-auth-check.yml` |
| `staging` | `movie-picker-ci-staging@` | les mêmes, étape `staging` |
| `backup` | `movie-picker-backup@` | `backup-mongo.yml` |
| `infra-apply` | `movie-picker-terraform@` | `infra.yml` sur master, job `apply`, derrière un relecteur requis |
| `infra-plan` | `movie-picker-terraform-plan@` | `infra.yml` sur une pull request, et les deux jobs de `plan` sur master |

- **`movie-picker-api@`**, l'identité d'exécution des révisions Cloud Run (`google_service_account.api_runtime`) : `secretAccessor` sur chacun des quatorze secrets (module `secrets`), aucun rôle sur le projet. `movie-picker-api-staging@` est son pendant de recette (section Recette).
- **`movie-picker-scheduler@`** (`google_service_account.scheduler`) : l'identité avec laquelle Cloud Scheduler signe le jeton OIDC des trois jobs de production. Aucun rôle nulle part ; sa valeur est son adresse, que l'API compare au champ `email` du jeton. `movie-picker-ci@` et `movie-picker-terraform@` portent `serviceAccountUser` dessus, le premier pour l'attacher aux jobs à chaque déploiement, le second pour le jour où Terraform les décrira (DEBT-037).
- **`movie-picker-ci@`**, l'identité que les workflows de déploiement assument (module `workload-identity`) : le jeton OIDC de GitHub est échangé contre elle par le pool `github` et son provider `github-actions` (module `github-federation`), qui n'acceptent qu'un job du dépôt, reconnu par son identifiant numérique autant que par son nom (un nom se libère par un renommage, l'identifiant jamais). Ses droits sont ceux que les workflows exercent, relevés commande par commande, et rien de plus : `run.developer` (déployer une révision, déplacer le trafic, lire les révisions ; pas de `setIamPolicy`, l'invocation publique est décrite ici), `cloudscheduler.admin` (les trois jobs, créés s'ils manquent, passés au jeton OIDC), `firebasehosting.admin`, `secretmanager.viewer` (l'existence d'un secret, jamais sa valeur) et `serviceusage.serviceUsageConsumer` (`x-goog-user-project`, la liste des API) sur le projet ; `serviceAccountUser` sur `movie-picker-api@` et `movie-picker-scheduler@` ; `artifactregistry.reader` sur le dépôt `movie-picker` seul (depuis le lot 8 la production ne pousse plus d'image, elle rescanne celle que la recette sert). Elle ne lit plus aucune version de secret et n'écrit plus le bucket de sauvegarde.
- **`movie-picker-backup@`** (`module "backup"`) : `secretAccessor` sur `MONGODB_URI` seul, `objectAdmin` sur le bucket de sauvegarde seul, `serviceUsageConsumer` sur le projet. C'est la seule identité de GitHub qui puisse lire la base de production, et elle ne sait rien déployer.
- **`movie-picker-terraform@`**, l'identité de l'`apply` sur master (workflow `infra.yml`, section suivante) : elle gère tout ce que le module racine décrit, donc `serviceUsageAdmin`, `serviceAccountAdmin`, `workloadIdentityPoolAdmin`, `projectIamAdmin`, `roleAdmin`, `run.admin`, `cloudscheduler.admin`, `artifactregistry.admin`, `firebasehosting.admin`, `monitoring.editor` et `lienModifier` sur le projet, plus deux rôles personnalisés qui lui refusent ce que les rôles prédéfinis auraient donné en trop : `secretsOperator` (créer, décrire et partager un secret, sans lire une version, avec la limite dite plus bas) et `bucketIamEditor` (la configuration et la politique d'un bucket, jamais ses objets, posé sur le bucket d'état et sur celui des sauvegardes) ; `objectAdmin` sur le bucket d'état ; `serviceAccountUser` sur `movie-picker-api@`, `movie-picker-api-staging@` et `movie-picker-scheduler@`. Elle n'a plus `firebase.viewer` : ce rôle, pris pour lire le projet Firebase, porte `storage.objects.get` sur tout le projet, donc la lecture des sauvegardes, ce que `firebasehosting.admin` (qui lit aussi le projet Firebase) ne porte pas.
- **`movie-picker-terraform-plan@`**, l'identité du `plan` sur une pull request : lecture seule, rôle par rôle plutôt que `viewer` ou `securityReviewer`, qui listent les objets des buckets et lisent les journaux : `run.viewer`, `secretmanager.viewer`, `monitoring.viewer`, `cloudscheduler.viewer`, `artifactregistry.reader`, `firebasehosting.viewer`, `workloadIdentityPoolViewer`, `serviceUsageConsumer` et le rôle personnalisé `planIamViewer` (les comptes de service, les rôles personnalisés et les politiques IAM du projet, de ses comptes et du dépôt d'images) ; `objectViewer` sur le bucket d'état, et le rôle personnalisé `bucketViewer` (la configuration et la politique d'un bucket, jamais ses objets) sur les deux buckets. Liée au seul sujet de l'environnement `infra-plan`, qui n'a ni politique de branche ni secret d'écriture, ce qui est précisément la raison de ne lui laisser aucun objet à lire.

Ce que ces droits ne garantissent pas : `movie-picker-terraform@` ne lit jamais une version de secret, mais elle en a le chemin. Partager un secret, c'est `setIamPolicy` dessus, et `projectIamAdmin` fait la même chose au niveau du projet : une identité fuitée se donnerait `secretAccessor` en un appel, que le journal d'audit des activités d'administration, impossible à désactiver, écrirait ; et depuis le 2026-09-20 la lecture elle-même s'écrit aussi, les journaux d'accès aux données de Secret Manager (`DATA_READ` et `DATA_WRITE`, `google_project_iam_audit_config`) étant activés, ce qu'ils n'étaient pas par défaut. Une politique de refus IAM (`secretmanager.googleapis.com/versions.access` refusé à `movie-picker-terraform@` et `movie-picker-terraform-plan@`, quels que soient leurs rôles) fermerait ce chemin ; elle demande une organisation Google Cloud, et un projet créé sous un compte personnel n'en a pas (`gcloud projects describe` sans `parent`, `roles/iam.denyAdmin` refusé sur le projet). C'est la limite de ce que le moindre privilège obtient ici, et elle vaut pour toute identité qui gère l'IAM du projet ; DEBT-050 tient le chemin qui la lève (une organisation, puis la deny policy).

Les secrets GitHub qui désignent ces identités sont des sorties des modules racines : `ci_service_account_email` (`GCP_SERVICE_ACCOUNT` de `production`, et celui de la racine `staging` pour l'environnement `staging`), `backup_service_account_email` (`GCP_SERVICE_ACCOUNT` de `backup`), `terraform_service_account_email` (`GCP_TERRAFORM_SERVICE_ACCOUNT` de `infra-apply`), `terraform_plan_service_account_email` (`GCP_SERVICE_ACCOUNT` de `infra-plan`), `scheduler_service_account_email` (le nom que `deploy.yml` connaît par `SCHEDULER_SERVICE_ACCOUNT_NAME`) et `workload_identity_provider` (`GCP_WORKLOAD_IDENTITY_PROVIDER` des cinq environnements). Après tout changement du pool, du provider ou des droits, `gh workflow run cloud-auth-check.yml --ref master` prouve les cinq échanges (deux étapes, sauvegarde, apply, plan) avant qu'un déploiement ne le découvre ; une liaison IAM fraîchement posée met une à deux minutes à être visible, un premier échec en `iam.serviceAccounts.getAccessToken` juste après un `apply` se rejoue.

Les API du projet dont tout cela dépend (`iam`, `iamcredentials`, `run`, `artifactregistry`, `secretmanager`, `cloudscheduler`) sont décrites et importées (`google_project_service.platform`, `disable_on_destroy = false`) : `deploy.yml` n'active plus rien lui-même. Le compte Compute par défaut, qui portait le pipeline jusqu'au 2026-09-20 avec neuf rôles sur le projet, `artifactregistry.admin` sur le dépôt et `objectAdmin` sur le bucket, n'a plus aucune liaison et est **désactivé** : l'audit du 2026-09-20 lui a trouvé, après le retrait de ses rôles, `secretAccessor` encore posé sur neuf secrets de production, liaisons d'avant l'identité d'exécution que le `plan` ne pouvait pas voir ; le compte `firebase-adminsdk-fbsvc@` créé par l'activation de Firebase, qui portait `serviceAccountTokenCreator` sur tout le projet (donc le pouvoir de frapper un jeton pour `movie-picker-terraform@`), est désactivé de même. **Terraform lie les membres un par un** (`google_*_iam_member`) : une liaison posée à la main, ou héritée d'avant la description, ne fait dériver aucun `plan`. `pnpm run check:iam` (section Portes) est la revue que le `plan` ne sait pas faire.

### Supervision (lot 7, importée le 2026-09-20)

Le module `monitoring` décrit ce que les alertes du projet sont, et le lie : les trois sondes de disponibilité (`/health` toutes les 60 s, `/health/ready` toutes les 15 minutes avec son ping MongoDB, le domaine canonique du front toutes les 5 minutes, depuis l'Europe, les USA et l'Asie-Pacifique), les sept politiques (trois sur les sondes, deux sur les métriques Cloud Run, une notification de nouveau compte lue dans les journaux structurés de l'API, et depuis le 2026-09-20 une passe planifiée en échec, lue dans les journaux de Cloud Scheduler : un 503 toutes les 30 minutes reste sous les seuils de l'alerte 5xx, que les sondes diluent, et les rappels de soirée cesseraient sans elle en silence), les canaux qu'elles notifient et le tableau de bord de MCO. L'identifiant d'une sonde est attribué par l'API à sa création : les conditions et les tuiles du tableau de bord le lisent sur la ressource (`uptime_check_id`) au lieu de le recopier, ce qui est la raison de les décrire ensemble. Recréer une sonde (un `monitoredResource` ne se modifie pas) repointe donc tout ce qui la lit dans le même `apply`.

La documentation de chaque politique, celle qui arrive dans l'e-mail d'alerte, vit ici en Markdown (`documentation.content`) : c'est elle que l'on relit avant de toucher un seuil, et les seuils y sont justifiés par les mesures qui les ont fixés. L'adresse notifiée est `ALERT_EMAIL` (`.env` local, secret des environnements GitHub `infra-apply` et `infra-plan` et de Dependabot), déclarée sensible : un `plan` l'affiche en `(sensitive value)`, et le premier `apply` après l'import a mis à jour le canal sans rien changer, pour que l'état porte cette sensibilité. Un second canal, par SMS, existe dès que `ALERT_SMS_NUMBER` (même trois emplacements, numéro au format E.164) est renseigné : un e-mail attend d'être lu, un texto non, et une alerte `CRITICAL` qui attend la prochaine lecture d'une boîte mail n'est pas une alerte. Vide, aucun canal SMS n'est décrit, et le `plan` d'une pull request, qui reçoit la même valeur, ne montre rien.

Une sonde qui reçoit un `301` compte comme en échec (`2xx` attendu) : la sonde du front vise le domaine canonique, jamais un alias qui redirige.

Une huitième politique, depuis le 2026-09-21, ne lit ni sonde ni journal de l'API : **« Sauvegarde MongoDB en retard »** observe les requêtes `MoveObject` réussies sur le bucket de sauvegarde (métrique `storage.googleapis.com/api/request_count`, le déplacement `pending/` vers `mongodb/` qui clôt `backup-mongo.yml` une fois la restauration vérifiée) et alerte quand il n'y en a eu aucune depuis 36 heures, par une condition PromQL (`absent_over_time(...[36h])`, évaluée toutes les 5 minutes). Les conditions d'absence classiques plafonnent à une journée, en deçà du retard quotidien que GitHub impose au cron ; et c'est le seul signal indépendant de GitHub que la sauvegarde part encore : un run rouge n'est signalé que par un e-mail de la plateforme, un run qui ne part plus (GitHub désactive les workflows planifiés d'un dépôt public sans activité pendant 60 jours) par rien. La requête se rejoue à la main pour vérifier qu'elle voit encore les déplacements (`POST https://monitoring.googleapis.com/v1/projects/<PROJET_GCP>/location/global/prometheus/api/v1/query`, paramètre `query`, jeton `gcloud auth print-access-token`) : elle rend une série valant `1` quand rien n'a bougé, rien sinon.

### Recette (lot 8, posée le 2026-09-20)

`environments/staging` est le second module racine, celui que le lot 1 annonçait : mêmes modules, même projet GCP, ressources suffixées `-staging`, un état à part. Il lit deux sorties de la production par `terraform_remote_state` (le pool de fédération avec ses sujets, le nom du dépôt d'images) : la recette ne décrit ni fédération ni dépôt, elle s'y lie, et c'est pourquoi `infra.yml` l'applique après la production, jamais à côté. Il décrit :

- **le service `movie-picker-api-staging`** (`api.staging.movie-picker.fr`, deux instances au plus : le pool Mongo de chaque instance compte dans le budget de connexions du cluster, C12 de `docs/technical-debt.md`) sous sa propre identité d'exécution, `movie-picker-api-staging@`, qui lit les cinq secrets propres à la recette et les six partagés qu'elle monte, jamais la base de production ; `movie-picker-terraform@` reçoit `serviceAccountUser` sur ce compte, décrit ici, sans quoi il ne peut pas créer un service qui tourne sous lui. Le service naît avec l'image `hello` de Cloud Run et sans secret monté (un secret sans version fait échouer la révision, et les versions s'ajoutent à la main après l'`apply`) : le premier déploiement le remplit, comme pour la production le pipeline garde le conteneur ;
- **cinq secrets `STAGING_*`** (module `secrets`) : la base, `STAGING_MONGODB_URI` (base `moviepicker_staging` sur le même cluster, utilisateur Atlas limité à cette base, `maxPoolSize=10` dans l'URI), et les deux clients OAuth de la recette (`STAGING_OAUTH_GOOGLE_*`, `STAGING_OAUTH_GITHUB_*` : GitHub n'accepte qu'une URL de rappel par OAuth App, et le secret Google de production ne se monte pas en recette). Les six partagés (`TMDB_API_KEY`, `RESEND_API_KEY`, `SENTRY_DSN`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `GITHUB_TOKEN`) reçoivent un second `secretAccessor`, celui de l'identité de recette. Partager `RESEND_API_KEY` est un choix : la recette envoie de vrais courriels depuis `movie-picker.fr`, ce qui permet d'y jouer la réinitialisation de mot de passe de bout en bout, au prix d'un courriel réel vers toute adresse qu'on y saisit ; `EMAIL_PROVIDER=log` dans `deploy.yml` (étape `staging`) les enverrait dans les journaux à la place. Ni `SCHEDULER_TOKEN` (aucun job Scheduler ne vise la recette, trois de plus sortiraient du palier gratuit, ses routes `/scheduler/*` répondent 503), ni `KOFI_WEBHOOK_TOKEN` (Ko-fi ne parle qu'à la production), ni `AUTH_DATAPROTECTION_KEYRING` (DEBT-045) ;
- **le site `movie-picker-web-staging`** (`staging.movie-picker.fr`, sans alias), publié avec `X-Robots-Tag: noindex, nofollow` sur chaque réponse (`--header` de `publish-front-firebase.mjs`, posé par `deploy-front` en recette) ; `verify-front` exige cet en-tête en recette et le refuse en production, pour qu'une configuration de recette ne sorte jamais le site de l'index ;
- **`movie-picker-ci-staging@`**, l'identité que `deploy.yml` assume depuis l'environnement GitHub `staging` (politique de branche `master`, comme `production`) : `run.developer` sur le seul service de recette (liaison posée sur le service, pas sur le projet), `artifactregistry.writer` sur le dépôt partagé (c'est elle qui pousse l'image), `firebasehosting.admin` et `serviceUsageConsumer` sur le projet, `serviceAccountUser` sur `movie-picker-api-staging@`. Hosting n'a pas d'IAM par site : le site de production est la seule ressource de production que cette identité pourrait atteindre, limite connue du choix « même projet », retenu parce qu'un second projet aurait demandé sa facturation, ses conditions Firebase et son écran de consentement OAuth pour une isolation que rien d'autre ne demande.

Rien d'autre : ni sonde ni politique d'alerte (le module `monitoring` n'est pas instancié), ni sauvegarde. Les deux workflows de retour arrière prennent une entrée `stage` : c'est en recette qu'un retour arrière se répète avant le jour où la production en a besoin, un retour arrière jamais exercé n'étant qu'un runbook. Aucun service ne sort de son palier gratuit ; seules les versions de secret comptent (0,06 $ par version active et par mois au-delà des six gratuites, une version désactivée compte encore, seule une version détruite ne compte plus), cinq de plus.

**Un déploiement passe par la recette avant la production.** `deploy.yml` prend une entrée `stage` : `staging` construit l'image, la scanne, la pousse en `api:<sha>` et la déploie, puis publie le front ; `production` refuse tant que la recette ne sert pas exactement ce commit (release de l'API lue sur `/health/ready`, release du front lue dans `<meta name="release">` de l'index servi, posée au build par `vite.config.ts` quand `SENTRY_RELEASE` est donné), puis redéploie le digest de la révision que la recette sert, relu sur cette révision avec la release dont elle a été construite (le tag `api:<sha>` nommerait la dernière image poussée, qui n'est pas celle servie quand une mise en recette a échoué à la validation), rescanné mais jamais reconstruit : ce qui a passé la recette est ce que la production exécute. La porte lit la release de l'API quel que soit le code de réponse : une base de recette injoignable donne un 503 avec le même corps, et un incident de recette ne retient pas un correctif de production. Lighthouse ne se joue qu'à la mise en recette (la mesure d'un build local, la même quelle que soit l'étape) : la production exige que la recette serve ce commit, donc que cette porte l'ait laissé passer. Les deux étapes ne diffèrent que par l'environnement GitHub de leurs jobs (identité, `VITE_API_URL`, `ALLOWED_ORIGINS` posée en variable de l'environnement `staging`, qui prime sur celle du dépôt) et par les noms de leurs cibles, en tête du workflow ; `gh workflow run cloud-auth-check.yml --ref master` prouve les deux échanges de jeton.

Ce qui s'est fait à la main, une fois, et ne se décrit pas : l'utilisateur Atlas de la recette, les deux clients OAuth (rappels `https://api.staging.movie-picker.fr/signin-google` et `https://api.staging.movie-picker.fr/signin-github`, les chemins de rappel des gestionnaires ASP.NET dans `AuthenticationExtensions.cs`), les cinq versions de secret (`gcloud secrets versions add STAGING_<NOM> --data-file=<FICHIER_SUPPRIME_ENSUITE>`), les enregistrements DNS chez OVH que `pnpm run terraform -- --root staging output web_dns` et `output api_dns` dictent, l'inscription de `movie-picker-terraform@` parmi les propriétaires vérifiés de `movie-picker.fr` (Search Console : un mappage de domaine Cloud Run n'est créé que par un propriétaire vérifié du domaine, et c'est cette identité qui l'a créé), et l'environnement GitHub `staging` avec ses secrets (`GCP_PROJECT_ID`, `GCP_SERVICE_ACCOUNT`, `GCP_WORKLOAD_IDENTITY_PROVIDER`, `VITE_API_URL`, `VITE_SENTRY_DSN`) et sa variable `ALLOWED_ORIGINS`.

### Plan en PR, apply sur master (lot 6, posé le 2026-09-20)

[`../.github/workflows/infra.yml`](../.github/workflows/infra.yml) est le seul endroit d'où l'infrastructure est changée par Terraform une fois un lot fusionné :

- **sur une pull request qui touche `infra/terraform/`, le workflow ou son action composite**, un `plan` de chaque module racine, en lecture seule et sans prendre le verrou (`-lock=false`), publié en commentaire de la PR (un commentaire par module racine, réédité à chaque push, retrouvé par sa première ligne). Le verdict est en tête : rien à changer, des changements à lire, ou un plan en échec qui met le job en rouge. Un plan qui montre des changements que la PR ne décrit pas est une dérive de l'infrastructure réelle, à corriger avant de fusionner. Les PR Dependabot (montées de providers) le jouent aussi : leurs secrets sont ceux de Dependabot, posés avec les mêmes noms ;
- **sur master**, depuis le 2026-09-21, deux jobs de `plan` d'abord (une racine chacun, lecture seule, sans verrou, sous l'identité de `infra-plan`, résumé de job avec les identifiants remplacés), puis le job `apply`, derrière l'environnement `infra-apply`, que seul ce workflow utilise et qui exige un relecteur (Settings / Environments / infra-apply / Required reviewers) : le job attend un clic dans l'onglet Actions, et ce clic se donne après lecture des deux résumés. Il replanifie alors sous le verrou, `plan -out` puis `apply` de ce fichier, la production puis la recette (qui lit les sorties de la production) : ce qui est appliqué est exactement ce que son propre résumé montre, et un écart avec le résumé lu avant le clic est une dérive survenue entre les deux. Deux plans vides sautent le job, donc le clic. Le fichier de plan ne voyage pas entre les jobs : un artefact d'un dépôt public se télécharge, l'état qu'il porte non. Un run qui attend son relecteur laisse master et l'infrastructure en désaccord jusqu'au clic, et GitHub l'échoue au bout de 30 jours : approuver ou refuser, jamais laisser attendre. Le même chemin se rejoue à la main (`gh workflow run infra.yml --ref master`) pour constater une dérive sans rien changer dans le dépôt : deux plans vides, aucun clic.

Les trois chemins partagent l'action composite [`../.github/actions/terraform-plan`](../.github/actions/terraform-plan/action.yml) (installation, `init` sur l'état distant, `plan -detailed-exitcode` dont le code est la sortie de l'action, la forme publique du plan (lignes de rafraîchissement retirées, identifiant et numéro de projet et bucket d'état remplacés par leurs espaces réservés), le résumé de job avec `summary`, et avec `apply` l'application du plan sauvegardé). Ce qui en découle pour un lot : décrire, `plan` en local pour construire, puis pousser ; l'`apply` local reste possible (le compte propriétaire y lit et y écrit encore), et le job de master retrouve alors deux plans vides. Seul le job `apply` porte un groupe de concurrence : deux applies ne se recouvrent jamais, et les plans, qui ne prennent pas le verrou, n'attendent rien. Une liaison IAM fraîchement posée met une à deux minutes à être visible : un premier échec en `iam.serviceAccounts.getAccessToken` juste après un `apply` se rejoue.

### Sauvegardes, lien et journaux d'audit (2026-09-20)

Le bucket de sauvegarde est décrit et importé (`google_storage_bucket.backups`) : accès uniforme, accès public interdit, versionnage, suppression réversible de sept jours, et deux règles de rétention, 30 jours pour les archives quotidiennes (`mongodb/`) et la zone d'attente (`pending/`), 400 jours pour `monthly/`, où `backup-mongo.yml` recopie la première archive vérifiée de chaque mois : une corruption remarquée après un mois avait jusque-là déjà emporté la dernière copie saine. Le workflow tourne dans l'environnement `backup`, sous `movie-picker-backup@`, section Identités.

Un lien (`google_resource_manager_lien`) interdit la suppression du projet, qui emporterait la production, ses sauvegardes et les états d'un seul geste : supprimer le projet demande d'abord de retirer le lien, un geste distinct. Les journaux d'accès aux données de Secret Manager sont activés (`google_project_iam_audit_config`) : chaque lecture d'une version de secret s'écrit, et se lit avec `gcloud logging read 'protoPayload.methodName="google.cloud.secretmanager.v1.SecretManagerService.AccessSecretVersion"'`. Ceux de Cloud Storage le sont aussi depuis le 2026-09-21 (`DATA_READ` et `DATA_WRITE`) : les archives de sauvegarde sont des données personnelles, et qui en lit une s'écrit désormais (`gcloud logging read 'resource.type="gcs_bucket" AND protoPayload.methodName="storage.objects.get"'`), comme chaque lecture et écriture des états Terraform.

Ce qui reste hors de Terraform parce que hors du projet : le budget d'alerte de facturation, posé le 2026-09-20 sur le compte de facturation (5 € par mois filtrés sur le projet, notification aux administrateurs du compte à 50 % et 100 % de la dépense constatée et à 100 % de la dépense prévue : le seul signal qui précède la facture quand un service quitte son palier gratuit, `gcloud billing budgets list --billing-account=<COMPTE_DE_FACTURATION>` le relit), et une organisation Google Cloud, qui donnerait les politiques de refus et `iam.disableServiceAccountKeyCreation`.

### Portes

`pnpm run check:terraform` ([`../scripts/check-terraform.mjs`](../scripts/check-terraform.mjs)) joue `terraform fmt -check -diff -recursive` sur tout `infra/terraform/`, puis `init -backend=false -lockfile=readonly` et `validate` sur chaque module racine de `environments/`, découverts par lecture du dossier. Ni bucket ni identifiants : la porte ne parle jamais à GCP. Elle est jouée dans `verify:local` (voie docker) et rejouée par le job `lint-terraform` de `ci-cd.yml`, à la même version de Terraform, avec le binaire de `hashicorp/setup-terraform`.

`pnpm run check:iam` ([`../scripts/check-iam.mjs`](../scripts/check-iam.mjs)) relit, avec le compte propriétaire, chaque liaison IAM du projet, des deux buckets, des secrets, des comptes de service, du dépôt d'images et des services Cloud Run, et signale tout membre que ce dossier ne décrit pas (les comptes `movie-picker-*@`, le propriétaire, les agents de service Google et les sujets de la fédération sont attendus, `allUsers` seulement en `run.invoker`), toute clé de compte de service, tout compte non décrit encore actif, et tout secret dont la dernière version a plus d'un an. Jouée dans la passe hebdomadaire : c'est la revue que `terraform plan` ne sait pas faire, les liaisons étant décrites membre par membre.

Deux familles de versions, deux mécanismes :

- **les providers** (`required_providers` dans `versions.tf`) sont suivis par Dependabot (écosystème `terraform`, un groupe mensuel). Après une montée de version, `.terraform.lock.hcl` doit porter les nouvelles empreintes : `pnpm run terraform -- providers lock`, à committer ; jusque-là la porte refuse le fichier de verrouillage en lecture seule ;
- **le binaire Terraform** est épinglé partout où il est nommé, et tous doivent dire la même version : `TERRAFORM_VERSION` dans `ci-cd.yml` et dans `infra.yml`, le tag de l'image dans `scripts/terraform.mjs` (digest compris) et `required_version` dans chaque `versions.tf`. `pnpm run check:tools` les compare entre eux et à la dernière version publiée, dans la passe hebdomadaire.
